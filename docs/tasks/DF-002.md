# DF-002 — 일정 로컬 알림

상태: 구현 완료 / 실기기 QA 대기 — docs/VALIDATION.md 참조

## 목적

사용자가 알림을 켠 일정의 시작 시간에 기기 내 알림을 예약하고, 일정 변경에 맞춰 예약을 갱신한다.

## 사용자 동작

1. 일정 편집 화면에서 `시작 시간에 알림`을 켠다. 새 일정의 기본값은 꺼짐이다.
2. 권한을 요청한 적이 없다면 이 조작 시 시스템 알림 권한을 요청한다. 앱 시작만으로 요청하지 않는다.
3. 권한이 허용되면 저장 성공 후 알림을 예약한다. 편집 취소 시 예약하지 않는다.
4. 권한이 거부되면 `알림 권한이 꺼져 있어요`와 설정 이동 버튼을 표시한다. 일정 자체는 저장할 수 있다.
5. 시간이나 제목을 수정하면 기존 알림을 갱신한다. 삭제·완료·알림 끄기는 예약을 취소한다.
6. 앱 설정에서 권한을 바꾼 뒤 돌아오면 상태를 새로 확인한다.

## 동작 규칙

- 알림 시점은 일정 시작 시간이다. 사전 알림, 반복 알림, 서버 푸시는 이번 범위에 포함하지 않는다.
- 알림 활성화 여부는 사용자 의도로 저장하고, OS 권한 상태나 예약 성공 여부와 구분한다.
- 일정 ID에서 파생한 안정적인 요청 식별자를 사용한다. 같은 일정을 다시 저장해도 중복 예약하지 않는다.
- 예약 대상은 알림이 켜진 미완료 일정 중 시작 시간이 현재 시각보다 미래인 일정이다. 현재 시각과 같거나 과거이면 예약하지 않는다.
- 완료를 취소하면 미래 일정만 다시 예약한다.
- 알림 내용에는 일정 제목을 표시하고 메모는 포함하지 않는다. 앱이 전면에 있을 때도 배너 표시를 지원한다.
- 일정의 Date가 가리키는 절대 시각을 기준으로 한다. 시간대 이동 후에도 같은 순간에 알린다. 시계 변경 이후에는 앱 활성화 시 재평가한다.
- 앱 시작 및 다시 활성화할 때, 불러오기에 성공한 저장 데이터와 현재 권한을 기준으로 예약을 맞춘다. 이 과정에서는 권한 팝업을 띄우지 않는다.
- 권한 거부나 요청 실패 후에도 사용자가 켠 알림 의도는 유지한다. 설정에서 권한을 허용한 뒤 앱으로 돌아오면 미래 일정 예약을 재시도한다.
- 앱이 관리하는 식별자의 알림만 갱신·취소한다. 다른 기능의 알림을 일괄 삭제하지 않는다.
- 초기 구현의 예약 상한은 32개로 정하고 시작 시간이 가까운 순으로 예약한다. 상한 초과 시 일부 일정의 알림이 대기 상태임을 설명한다. 앱 활성화 및 일정 변경 시 다시 선정한다. 앱을 계속 열지 않으면 대기 일정이 자동 보충되지 않는 제한을 README에 명시한다.

## 저장과 실패 처리

- 일정 저장에 성공한 뒤 알림 동기화를 수행한다. 저장 실패 시 기존 예약과 저장 데이터를 유지한다.
- 삭제 저장이 실패하면 기존 알림을 취소하지 않는다.
- 알림 예약 실패는 일정 저장 실패와 구분한다. `일정은 저장했지만 알림을 예약하지 못했어요`와 재시도 동작을 제공한다.
- 삭제·완료·알림 끄기 시 해당 일정의 미전달 예약과 이미 전달된 알림을 정리한다.
- 알림 처리 중 연속 수정·삭제가 발생해도 마지막으로 저장된 상태가 최종 예약에 반영되도록 작업 순서를 보장한다.
- 불러오기에 실패한 경우 빈 목록을 정상 데이터로 취급해 기존 알림을 삭제하지 않는다.

## 화면 요구사항

- 편집 화면에 알림 토글과 권한 상태 안내를 추가한다.
- 권한 거부 시 설정 이동은 사용자 버튼 조작으로만 실행한다.
- 과거 일정은 저장 가능하되 알림이 예약되지 않는 이유를 안내한다.
- 권한 요청/예약 처리 중 중복 실행을 방지하고 UI를 차단하지 않는다.
- 알림 도착 시간은 시스템 설정과 실행 환경의 영향을 받을 수 있음을 README에 설명한다. 예약 성공을 실제 수신 성공으로 표시하지 않는다.

## 구현 범위와 제약

- Core/: 알림 활성화 필드, 기존 데이터 디코딩 호환성, 예약 대상 선정 로직.
- App/: UserNotifications 어댑터, 권한 처리, Store와 저장 후 동기화 연결, 편집 UI 및 앱 활성화 처리.
- Tests/: 현재 시각과 권한·예약 클라이언트를 주입하여 동작과 실패 경로 검증.
- 새 필드가 없는 기존 JSON은 알림 꺼짐으로 읽는다. 기존 ID와 데이터를 보존한다.
- 시스템 API와 순수 로직을 분리해 macOS의 Swift Package 테스트를 유지한다.
- --demo 및 --error-demo는 실제 권한을 요청하거나 기기에 알림을 예약·취소하지 않는다. 가짜 클라이언트로 성공·거부·실패 상태를 재현한다. 실행 방법을 README에 기록한다.
- DF-001 구현 여부와 무관하게 진행할 수 있다. 검색 기능을 변경하지 않는다.
- 구현 전 Apple 공식 문서에서 권한 상태, 예약·취소 API와 제한을 확인한다. Focus·알림 요약·사용자 설정을 우회하지 않는다.

## 완료 조건

- [ ] 사용자 토글 조작 시에만 최초 권한 요청을 실행한다.
- [ ] 미결정·허용·거부·제한된 허용 상태를 명시적으로 처리한다.
- [ ] 거부 상태에서도 일정을 저장할 수 있고 설정 이동을 제공한다.
- [ ] 미래·미완료·알림 활성 일정만 시작 시간에 예약한다.
- [ ] 수정 시 중복 없이 갱신하고 삭제·완료·알림 끄기 시 취소한다.
- [ ] 저장 실패 시 예약 상태를 변경하지 않는다.
- [ ] 예약 실패를 일정 저장 성공과 구분해 안내하고 재시도한다.
- [ ] 재시작·다시 활성화·권한 변경 시 저장 데이터 기준으로 예약을 맞춘다.
- [ ] 연속 변경 시 마지막 저장 상태와 예약 상태가 일치한다.
- [ ] 예약 상한과 대기 항목 처리 및 제한을 설명한다.
- [ ] 이전 JSON 파일을 읽을 수 있고 데모가 실제 알림에 영향을 주지 않는다.
- [ ] 핵심 테스트와 기존 테스트, iOS Simulator 대상 빌드가 통과한다.
- [ ] 전면·백그라운드의 실제 기기 알림 도착을 각각 확인하거나 미검증으로 명시한다.

## 검증 계획

자동 테스트:

- 최초 요청은 사용자 조작에만 발생하며 반복 요청하지 않음.
- 권한 허용·거부·권한 요청 오류 및 예약 오류 처리.
- 미래/현재/과거, 완료/미완료, 알림 켜짐/꺼짐의 예약 대상 선정.
- 같은 ID 재저장, 제목/시간 변경, 삭제, 완료와 완료 취소.
- 저장 실패 시 알림 클라이언트를 호출하지 않음.
- 예약 실패 후 재시도, 빠른 수정 직후 삭제의 최종 상태.
- 기존 JSON에 새 필드가 없을 때 기본값 적용.
- 32개 상한과 가까운 일정 우선 선택, 재동기화의 중복 방지.
- 불러오기 실패 시 취소하지 않음, 데모 모드에서 실제 클라이언트 미사용.

실행 명령:

```sh
./scripts/verify.sh
```

수동 확인:

1. 권한 미결정 상태에서 앱 실행만으로 팝업이 나오지 않는지 확인한다.
2. 미래 일정의 알림을 켜 권한 허용 후 저장하고, 전면/백그라운드 수신을 확인한다.
3. 편집 취소와 제목·시간 수정 후 취소된/이전 내용의 알림이 도착하지 않는지 확인한다.
4. 삭제·완료·알림 끄기 이후 예약이 제거되는지 확인한다.
5. 권한 거부 후 일정 저장, 안내, 설정 이동 및 다시 허용 후 예약을 확인한다.
6. 과거 일정, 저장 실패, 알림 예약 실패·재시도를 확인한다.
7. 앱 재실행, 시간대 변경, 상한 초과 및 데모 모드를 확인한다.

QA 계획은 이 TASK를 기준으로 한다. 반복 확인할 항목만 docs/QA.md에 추가하고, 실제 실행 환경·권한·결과·미검증 사유는 docs/VALIDATION.md에 기록한다. 별도 DF-002 QA 문서를 중복 작성할 필요는 없다. 기기 수신을 확인하지 못했다면 예약 API 성공만으로 전체 검증 완료로 처리하지 않는다.
